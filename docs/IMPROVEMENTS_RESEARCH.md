# HYPE v3 — Исследование и план повышения качества отбора монет

> **Статус (раунд 5, реализовано):** сохранены улучшения раунда 4 и добавлены
> четыре практических фикса: (1) RVOL сравнивает последний бар с базой без
> самого последнего объёма, (2) live data-service отбрасывает формирующуюся
> свечу, (3) emergence различает `EARLY`, `TRIGGERED`, `EXHAUSTED` по давлению
> закрытия, сжатию, пробою коридора и запасу до границы, (4) daemon запускает
> тот же Scanner по всей ликвидной вселенной, а явный `watch SYMS` остаётся
> точечным. В скоринг добавлен независимый `Impulse Readiness`, а объёмный
> фактор использует RVOL/OBV/CVD/MFI вместо одного z-score. Всегда остаются
> инварианты: только реальные данные, no-execution, deterministic gate и
> backtest/live parity.
>
> Раунд 4 уже реализовал P0-1 (DI±, EMA-stack, MFI, BB %B, W%R, ROC,
> MACD/Stoch-кроссы, RVOL), P0-2 (BOS/CHoCH), P0-4
> (RVOL/squeeze-release/консолидация/dpos/RS + anti-chase + диверсификация +
> возраст листинга), часть P1-3 (OI×funding×цена, ускорение ликвидаций).
> Следующие исследовательские этапы (не заявляем как сделанные): P1-1
> реальный WS public-trade CVD, P1-2 volume profile, P2-1..P2-3 строгая
> статистика, ML-1.

> Документ-результат глубокого аудита кода + analysis вендора и перспективных
> open-source проектов. Цель: **что изменить, чтобы бот отбирал монеты лучше и
> давал более качественные результаты**, не ломая уже принятые инварианты
> платформы (только реальные данные, no-execution, детерминированный гейт,
> AI-слой только для объяснений, backtest/live parity, no look-ahead).
>
> Формат: сначала **честный аудит текущего состояния** (что реально теряет
> качество), затем **что дают референсы с GitHub/интернета**, затем
> **согласованный (непротиворечивый) план** с приоритетами, потом — что делать
> **нельзя**. В конце — метрики успеха и список файлов.

## 0. TL;DR (коротко)

Система уже **сильная** (детерминированный гейт, реальные данные, no-lookahead,
walk-forward, тир-списки). Главные потери качества сейчас — не «мало индикаторов»,
а **четыре системные проблемы**:

1. **~45% веса скоринга — один и тот же тренд** (Trend Alignment 15 + Market
   Structure 15 + Momentum 15 частично = один признак × 3). Больше данных о
   рынке не значит больше информации: факторы дублируются и «шумят».
2. **Вычисляем, но не используем**: OBV-тренд, OI-change 24h, DI±, MACD-кросс,
   Stoch-D, BB %B, ROC, MFI, W%R, EMA 50/200 — всё уже посчитано в индикаторах,
   но не доходит до скоринга. Мёртвые конфиги: `MAX_CORRELATED_POSITIONS`,
   `BTC_CORRELATION_PENALTY_THRESHOLD`, `MIN_ORDERBOOK_DEPTH_USD`,
   `MIN_BID_ASK_LEVELS`, `SHOW_TIER_MIN`.
3. **Отбор монет = «heat по 24h %»**: сканер в основном ловит монеты *после*
   движения (chase), игнорирует RVOL, относительную силу, OI-динамику, возраст
   листинга и — главное — **корреляцию** (10 «топ-возможностей» часто = 10
   одинаково коррелированных альтов; конфиг для этого уже есть, но не подключён).
4. **Обратная связь не замкнута**: TP/SL-исходы (R-multiple) пишутся в SQLite,
   но никто не считает «score → реальная вероятность выигрыша» и не проверяет
   дрейф качества. `quality=80` сейчас — «мнение модели», а не калиброванная
   вероятность.

План ниже закрывает 1–4 последовательно: **P0** — бесплатные/дешёвые улучшения
(использовать уже вычисленное, починить дубли, включить диверсификацию),
**P1** — новые данные с реальных общедоступных фидов (publicTrade WS,
funding-история, volume profile, RVOL/RS, OI-матрица), **P2** — статистически
строгая валидация (purge/embargo, bootstrap, Monte Carlo) и опциональный
ML-слой, который по умолчанию **выключен** и не трогает детерминированный гейт
(с явной оговоркой об изменении инварианта №3 — см. §7).

## 1. Как сейчас работает отбор (карта, по коду)

```
tickers (Bybit→Binance→MEXC)
  └─ Scanner._rank_candidate   heat = f(24h %, turnover, 24h range, funding, spread)
       └─ top-N (SCAN_TOP=20) → FuturesSignalEngine.analyze_batch
            ├─ build_timeframe_view (5m/15m/1h/4h/1d)  → TimeframeView
            ├─ detect_regime (правила по ADX/ATR/vol_z/squeeze)
            ├─ analyze_derivatives (funding, OI, L/S, ликвидации)
            ├─ analyze_orderflow (REST-снапшот стакана, CVD-прокси по OHLCV)
            ├─ build_context (BTC 1h + ETH 24h + доминация/новости)
            ├─ build_levels (ATR + структура) → R:R
            ├─ score_signal (9 факторов, веса 15/15/15/12/10/10/10/6/7)
            └─ apply_direction_gate + apply_risk_reward_gate → CONFIRMED | NO TRADE
```

Сильные стороны (не трогаем): единый `evaluate_bundle` для live/backtest,
детерминированный NO-TRADE, отсутствие синтетики, TTL-кэши, degraed-детекция,
реальные ликвидации через WS, тир-списки для UI.

## 2. Аудит: где именно теряется качество

### 2.1 Индикаторы считаются — но не доходят до модели

`src/data/indicators.py::compute_all` уже считает:
`rsi_14, macd(+signal/hist), stoch_k/stoch_d, roc_20, wpr_14, atr_14(+pct/pctl),
bb_mid/up/low/width/pctb, kc, rv_20, adx(+plus_di/minus_di), supertrend,
vwap, obv, cvd, mfi_14, vol_z, obv_trend, cvd_trend, ema_9/20/50/200`.

А `v3/analysis/timeframes.py::build_timeframe_view` пробрасывает в
`TimeframeView` только **12 полей**, причём:
* `obv_trend` — есть в модели, но **нигде не участвует** в скоринге/режиме
  (grep: только `timeframes.py` + `models.py`; в `scoring.py`/`regime.py`
  отсутствует).
* `plus_di / minus_di` — есть в `StructureState` (v1), но **не попали** в
  `TimeframeView`, поэтому мульти-ТФ-выравнивание по `DI` невозможно.
* `macd_cross`, `stoch_d`, `bb_pctb`, `roc_20`, `wpr_14`, `mfi_14`,
  `ema_50/200`, `rv_20`, `bb_width` — вычислены, но **полностью игнорируются**
  v3-моделью.

**Вывод:** «добавить индикаторы» во многом уже сделано на уровне сырых данных —
надо **экспонировать и использовать** то, что есть. Это бесплатный прирост
ортогональной информации (объём против тренда: OBV/MFI/BB %B; сила тренда: DI,
EMA-stack; разворотные триггеры: MACD-кросс, Stoch-кросс, W%R).

### 2.2 Дублирование факторов в скоринге

`v3/analysis/scoring.py`:

| Фактор | Вес | На чём основан | Пересечение |
|---|---|---|---|
| Trend Alignment | 15 | `v.trend` (а тот = ADX+DI из `market_structure`) | с Market Structure |
| Market Structure | 15 | `macro.trend`, `structure_signal` | с Trend Alignment |
| Momentum | 15 | `macd_hist`, `supertrend`, `rsi` | снова тренд |
| Volume | 12 | только `vol_z` | не использует OBV/CVD |
| Volatility | 10 | `atr_pct`, squeeze | ок |
| Order Flow | 10 | `orderflow.score` | включает CVD-прокси |
| Derivatives | 10 | `derivatives.score` | funding/L/S; **без OI** |
| Liquidity | 6 | book grade, turnover | ок |
| Market Context | 7 | BTC/ETH | ок |

Это и есть «почему противоречит само себе»: три фактора из четырёх самых
тяжёлых измеряют один и тот же тренд, при этом **объёмная/флоу-сторона
(OBV, MFI, BB %B, DI, EMA-stack, OI) не представлена вообще**. Диверсификация
признаков даёт больше, чем весы 15/15/15.

### 2.3 Деривативы: есть все данные, но нет главного признака

`v3/analysis/derivatives.py`:
* `oi_change_24h_pct` теперь считается из live-истории OI и используется в
  positioning-матрице и emergence. Важно: `open_interest_history` хранит
  сырые значения OI, а не проценты; преобразование должно быть единым.
* funding работает как «перегрев» (порог ±0.2%/-0.1%), а матрица
  **OI × funding × цена** добавляет контекст построения/перегрева/капитуляции
  (см. §3.6): рост OI + рост цены + нейтральный funding = здоровое построение
  позиции; рост OI + падение цены + высокий positive funding = накопление
  ликвидаций лонгов (риск каскада); падение OI + падение цены = капитуляция
  (часто разворот вверх).
* `liq_count`/сумма ликвидаций есть, но скоринг учитывает только imbalance и
  не смотрит на **абсолютный размер** и **динамику** (увеличение ликвидаций
  за последние минуты).
* `long_short_ratio` назван `taker_buy_sell_ratio` в модели — это просто
  account ratio Bybit, **не** taker-ratio. Косметическая, но опасная путаница
  (легко «использовать» как реальный buy/sell-флоу — это не так).

### 2.4 Order flow: снапшот + прокси вместо потока

`v3/analysis/orderflow.py` использует REST-снапшот 50 уровней 1 раз и:
* `imbalance` — только по 1% глубины, одно окно;
* `cvd_trend` — **прокси по OHLCV** (`cvd()` в indicators.py: распределение
  объёма бара по позиции close в диапазоне), а не реальная дельта сделок;
* нет microprice, наклона стакана (book slope), «стен/поглощений»,
  нет анализа сделок (принтов).

При этом **Bybit публичный WS `publicTrade`** (сделки) и **`orderbook.50`**
(снапшоты+дельты) доступны без ключей — и у нас **уже есть инфраструктура WS**
(`src/data/liquidations_ws.py`: один коллектор на процесс, reconnect+backoff,
буфер с биржевыми ts). Расширение её на `publicTrade` — это получение
**настоящего CVD/дельты, крупных сделок, спектра агрессии** — самый большой
реальный апгрейд «микроструктуры» без платных API.

### 2.5 Режим рынка (regime): правила с порогами, без статистики

`v3/analysis/regime.py` — детерминированные правила (ADX ≥ 22, ATR-процентиль,
vol_z, squeeze, «breakout если vwap_dist>0.3% и vol_z>0»). Это ок для
интерпретируемости, но:
* пороги жёсткие и **одинаковые для всех монет**, хотя у SOL ATR 2% — норма, а у
  старого альта 8% — уже экстрим (частично решает `atr_pctl`, но только по
  собственной истории монеты, без учёта BTC-фазы);
* `vol_state` в `regime.py` и `volatility_state` в v1 — **две разные логики**
  (первая по абсолютным `ATR_PCT_*`, вторая по процентилю) → возможны
  расхождения «regime says HIGH_VOLATILITY, vol_state says low» внутри одного
  отчёта;
* нет смены «режима на рынке» для всей вселенной (sector regime, alt-season,
  BTC-фаза), хотя данные для этого есть (`global_change_pct`, dominance).

### 2.6 Сканер: отбирает «уже разогретое», не «лучшее» через корзину

`v3/scanner.py::_rank_candidate`:
```
heat = +min(30, pct24h*2.5/+2.0)  ← почти половина веса = «вчерашний/сегодняшний рост»
     + min(25, log10(turnover)*2) ← ликвидность
     + min(15, range%*1.2)        ← волатильность
     + funding ±8  + spread ±6    − majors 4
```
Проблемы:
* **нет относительной силы**: монета +30% при BTC +5% и монета +12% при BTC
  −5% получают разный heat, но RS не учитывается вовсе; нет 7d/30d моментума;
* **нет RVOL** (объём последних 15м/1ч против своего же среднего) — а это
  классический «heat»-детектор, и он **не зависит от уже состоявшегося
  движения**;
* **нет OI-изменения** (поле уже читается в `_rank_candidate` в `open_interest`,
  но в heat не входит);
* **нет позиции в 24h-диапазоне**: монета у 24h-high с ретракцией 1% и монета,
  отскочившая на 20% от лоу, — оба «горячие», но сетапы разные
  (breakout-continuation vs mean-reversion);
* **нет возраста листинга** (`launchTime` есть в
  `GET /v5/market/instruments-info` у Bybit): первые дни листинга — отдельный
  высоковолатильный режим (часто pump&dump), его надо **маркировать**, а не
  молча включать в «топ»;
* **мажорный penalty — хардкод на 9 символов**; список устаревает и не учитывает
  ликвидностные тиры (S/A/B) — при этом конфиг `SHOW_TIER_MIN` есть, но не
  используется;
* **нет диверсификации**: `result.analyzed` сортируется по quality и просто
  режется; `MAX_CORRELATED_POSITIONS=3` и
  `BTC_CORRELATION_PENALTY_THRESHOLD=0.75` **объявлены, но нигде не
  применяются** — прямое противоречие между конфигом и поведением;
* нет блэк-листа «мусора» (токены с нереальным спредом/нулевым OI уже
  отсекаются, но гибридные/synthetic контракты, «мыльные пузыри» без depth —
  частично проходят по turnover).

### 2.7 Обратная связь есть, калибровки — нет

`v3/store.py` пишет `v3_outcomes` (exit_reason, mfe/mae, r_multiple, pnl_pct).
`v3/watcher.py` трекает TP/SL по ценам. Но **ни один модуль не использует
исходы** для:
* проверки «score 72+ действительно выигрывает чаще, чем score 55-65»;
* оценки каждого фактора отдельно (какой фактор реально несёт edge, а какой —
  шум);
* дрейфа (CUSUM) качества во времени.

Как следствие, в README честно написано «Signal Quality ≈ качество сетапа, **не
вероятность прибыли**» — и это правильно сейчас, потому что зависимость
score→исход никогда не измерялась. Замкнув этот контур, мы сможем **честно**
говорить «в этой калибровке score 80+ давал ~58% winrate» (или увидеть, что нет).

### 2.8 Backtest/Live parity — что реально покрыто

`run_backtest` создаёт `DataBundle` с `degraded=["funding unavailable",
"order book unavailable", "global context unavailable"]` и
`strict_liquidity=False`. Это значит:
* бэктест **не проверяет** большую часть того, что добавляет качество в live
  (derivatives=50.0 по умолчанию, orderflow=empty, контекст отсутствует);
* «parity» верна для **правил/уровней/гейта**, но **не для факторов**;
* любые улучшения orderflow-деривативов, которые мы предложим, **не будут
  валидироваться бэктестом**, пока не появится исторический
  derivatives-фид — это надо честно зафиксировать (см. §6.3), иначе получится
  «улучшение, которое мы не можем проверить» — худший вид улучшения.

### 2.9 Мелкие, но важные неточности

* **BOS/CHoCH эвристика** (`timeframes.py`): сигнал определяется цепочкой
  `if highs rising → BOS_UP; elif lows rising → CHoCH_UP; ...` — это не
  отличает **продолжение** (BOS по ходу тренда) от **первого разворота**
  (CHoCH против тренда). Из-за этого `scenarios.detect_choch_reversal` может
  срабатывать на обычном продолжении, а `structure_signal` — врать.
* **Stochastic построен на high/low без учёта close** в `structural`
  направлении — некритично, но при добавлении Stoch-кросса лучше использовать
  `%K/%D` на закрытии.
* **VWAP сессионный** (сброс на сутках UTC) — нормально, но на 5m для альтов
  с большим gap полезнее **rolling VWAP** (например, 24ч) как отдельный
  признак; сейчас `vwap_dist_pct` — только сессионный.
* `MIN_BID_ASK_LEVELS`, `MIN_ORDERBOOK_DEPTH_USD`, `SHOW_TIER_MIN` — не
  применяются (мёртвый конфиг).

## 3. Что берём из перспективных проектов (и почему)

Референсы выбирались по одному критерию: **решает ли проект нашу конкретную
проблему**, а не «модный ли он».

### 3.1 Freqtrade + FreqAI (53k★) — ML-слой, rolling retrain, purged CV

FreqAI — самая зрелая open-source адаптивная ML-обёртка над правилами:
rolling-окно обучения, отбор признаков, `include_timeframes`,
`include_corr_pairlist`, `label_period_candles`, SVM-фильтр аномалий,
`shuffle=False`, PCA. Плюс `hyperopt` (Optuna) с loss-функциями Sharpe/Calmar,
`edge`-модуль (оценка winrate-математики на сделку) и `lookahead-analysis` /
`recursive-analysis` (поиск утечек будущего в стратегии).
* **Берём:** концепцию **трёх независимых слоёв** (правила → признаковый
  мета-скоринг → риск/размер), rolling-обучение **только по закрытым барам**,
  `purge/embargo` (см. PyBroker ниже), инструменты анти-lookahead (хотя у нас
  уже есть parity и no-lookahead — усиливаем тестами).
* **Не берём:** FreqAI «из коробки» (другой стек, его цель — генерация
  сигналов, а не наш аналитический слой), и прямую замену нашего gate на
  ML-предсказание — это нарушит инвариант №3.
* Ссылки: [freqtrade](https://github.com/freqtrade/freqtrade),
  [docs FreqAI](https://docs.freqtrade.io/en/2026.3/freqai-running/),
  [пример institutional Mix: Triple-Barrier + SHAP + meta-labeling + purged CV](https://dev.to/stefano_viana_dda882cfae5/how-i-built-a-profitable-freqai-plugin-using-institutional-ml-techniques-1l9k).

### 3.2 Jesse (5k★) — «честный» бэктест, Optuna+Ray, Monte Carlo, significance tests

Ключевое в README Jesse: **zero look-ahead bias**, оптимизация через **Optuna
+ Ray parallel**, **Rule Significance Testing**, **Monte Carlo analysis**,
ML pipeline (обучение scikit на лейблах из бэктеста и использование
предсказаний как live-сигнала).
* **Берём:** а) **Monte Carlo** поверх наших бэктест-трейдов (перемешивание
  последовательности сделок → распределение maxDD/просадок — очень дёшево и
  сильно улучшает доверие к результатам); б) **significance-тест правила**
  (например: «входы по CHoCH лучше/хуже всей выборки?» — t-test/bootstrap на
  R-multiple); в) **оптимизацию порогов через Optuna** как замену ручного
  `calibrate` (read-only, с последующим walk-forward).
* **Не берём:** сам фреймворк (у нас свой движок) и «ML → live-сигнал» без
  пересмотра инварианта №3.
* Ссылка: [jesse-ai/jesse](https://github.com/jesse-ai/jesse).

### 3.3 OctoBot (5.4k★) — мульти-оценщики («ensemble evaluators»)

OctoBot строит сигнал как **взвешенную композицию многих оценщиков**
(TA-оценщики, social/news оценщики, MLTA-классификаторы на sklearn) и
«Trading Modes», которые решают, **как** комбинировать оценки, и имеют
обратную связь по качеству.
* **Берём:** идею **явного разделения «факторы → композитор → решение»**:
  наш `score_signal` уже композитор, но факторы не ортогональны (§2.2).
  А также идею **мягкой маркировки качества источника** — в выдаче помечать
  «деривативы: н/д», «объём: тайп-прокси» и т.п. (у нас частично есть).
* **Не берём:** соц.сети как полноценный оценщик (у нас новости — только
  контекст и только в `auto`; оставляем так: соцшум сложно верифицировать, и он
  не реальный «биржевой» сигнал).
* Ссылка: [Drakkar-Software/OctoBot](https://github.com/Drakkar-Software/OctoBot).

### 3.4 PyBroker (edtechre) — bootstrap CI, ranking, walkforward

PyBroker: walkforward-разбиения, **bootstrap-метрики** (BCa-доверительные
интервалы для Profit Factor/Sharpe/просадки), **Ranking** (выбор инструментов
по скорингу) и **Position Sizing**.
* **Берём:** (а) **bootstrap CI для наших метрик** — «PF = 1.4 [1.05, 1.9]»
  вместо «PF = 1.4» (это прямо отвечает на «более качественные результаты»);
  (б) **purged/embargo-разбиения**: сегодняшний `walk_forward` только
  *оценивает правила* (ничего не обучает), поэтому как «проверка правил» он
  честен; но как только появляется *обучаемый* слой (Optuna-веса, калибровка,
  ML — P2-2/ML-1), у признаков warm-up 100–200 баров (EMA-200, atr_pctl,
  zigzag) и fold-окна без паузы → нужен purge/embargo;
  (в) **roтационное ранжирование** как формальный каркас для сканера.
* Ссылки: [edtechre/pybroker](https://github.com/edtechre/pybroker),
  [Walkforward tutorial](https://medium.com/@edtechre/algotrading-in-python-with-machine-learning-walkforward-analysis-1ebfb8a9fcf0).

### 3.5 Микроструктура: cryptofeed / tardis / OrderFlow-Analysis-Pro / volume profile

* **cryptofeed** — объединяет WS-потоки бирж (trades, L2 book deltas, funding,
  OI, liquidations) в единый интерфейс; наглядно показывает, **какие данные
  реально доступны публично**. Наш аналог (own WS) уже есть — расширяем его на
  `publicTrade` и дельты стакана.
* **tardis.dev docs** подтверждают для Bybit Derivatives: **`publicTrade`**
  (с 2023-04-05) и **`orderbook.50`** (снапшоты+дельты) — значит, реальные
  сделки и обновления стакана доступны без подписки.
* **OrderFlow-Analysis-Pro (Fabio Testa)** — пять детекторов паттернов:
  **absorption, initiative, sweep, exhaustion, divergence**, объединённых в
  композитный score 0–100 с state-machine lifecycle. Прямо переносимая идея:
  наши «сценарии» (sweep, CHoCH) — 2 из 5; добавляем **absorption/exhaustion**
  и **дивергенцию цены и CVD** как отдельные понижающие/повышающие флаги.
* **Volume Profile** (bfolkens/py-market-profile — BSD, готовый эталон;
  TradingView-реализации с POC/VAH/VAL/intrabar): **POC/VAH/VAL** — самые
  полезные «уровни» после свингов: притяжение к POC, отторжение значений вне
  value area, «пробой VAH с объёмом» = подтверждённый пробой. У нас есть 1м/5м
  свечи и (после WS) реальные принты — построить профиль за 24ч/7д дёшево своё
  (60–100 строк), без новой тяжёлой зависимости.
* Ссылки:
  [cryptofeed](https://github.com/bmoscon/cryptofeed),
  [tardis Bybit docs](https://docs.tardis.dev/historical-data-details/bybit),
  [OrderFlow-Analysis-Pro](https://github.com/mahmoud20138/OrderFlow-Analysis-Pro),
  [py-market-profile](https://github.com/bfolkens/py-market-profile),
  [TradingView volume profile (Pine)](https://github.com/mervinj3546/volume-profile).

### 3.6 Деривативы: методология CoinGlass/Coinalyze и матрица OI×funding

CoinGlass/Coinalyze — индустриальный стандарт чтения фундамента перпов.
Ключевые паттерны (и их **ограничения**, которые мы обязаны честно
маркировать — heatmap это **модельные оценки**, не подтверждённые движком
биржи, искажаются хеджами на малоликвидных альтах):
* **Высокий positive funding + растущий OI** = перегрев лонгов → риск
  каскада/коррекции (сейчас мы штрафуем только сам funding, а не сочетание);
* **Отрицательный funding + растущий OI** = перегруз шортов → потенциал
  short-squeeze (у нас есть «+15» за низкий funding и «+8» за L/S<0.35, но нет
  OI-подтверждения);
* **Падение цены + падение OI + валидный negative funding** = капитуляция
  лонгов → часто разворот;
* Ликвидации: смотреть **не только imbalance, но и абсолют $ и ускорение**
  (буфер 15 мин уже есть — добавляем «рост ликвидаций за последние 5 мин»).
* CoinGlass Derivatives Risk Index (0–100) — ориентир, но **проприетарный**;
  мы можем реализовать свой открытый «derivatives-risk score» из наших же
  публичных данных (funding, OI-Δ, L/S, ликвидации) — лучше, чем платный вход.
* Ссылки: [What is Coinglass](https://cryptorank.io/news/feed/bf393-what-is-coinglass-crypto-liquidation-data-explained),
  [Funding + OI: how to spot liquidations](https://tradelink.pro/blog/funding-rate-open-interest/),
  [CoinGlass learn](https://www.coinglass.com/learn/how-to-judge-market-by-fr-en).

### 3.7 Режимы рынка: regimе-детекция через HMM / changepoint (hmmlearn, ruptures)

Перечисленные выше repository по market-regime (HMM/GMM/ruptures + walk-forward
валидация) — показательный **второй контур** поверх наших правил: статистическая
детекция смены режима (например, PELT/kernel CPP на логарифмических
доходностях, или 3-state Gaussian HMM на (return, vol, trend) — обучать на BTC
и на монете отдельно).
* **Берём** как **опциональный второй opinion** (`REGIME_MODEL=off|hmm|cpp`,
  по умолчанию **off**): если статистический детектор расходится с правилами —
  печатаем «⚠ regime disagreement — сниженная уверенность», но правила
  остаются главными (никакого конфликта с детерминированностью, потому что
  HMM ничего не блокирует и не запускает — это флаг).
* **Не берём**: обучение на полной истории с последующим тестом на ней же
  (это утечка; надо walk-forward), замену правил на «чистый ML-режим».
* Ссылки: [market-regime-detection (HMM+GMM+CP+WF)](https://github.com/Sakeeb91/market-regime-detection),
  [regimeshifts (early warning signals)](https://github.com/BeatrizArellano/regimeshifts),
  [awesome-systematic-trading](https://github.com/wangzhe3224/awesome-systematic-trading).

### 3.8 Академическая база (для надёжности, не для красоты)

* **López de Prado, «Advances in Financial ML»**: triple-barrier labeling,
  **meta-labeling** (модель предсказывает не направление, а **качество**
  сигнала: «стоит ли доверять этому A-сетапу»), **purged K-fold + embargo**,
  **deflated Sharpe ratio** — анти-оверфит инструменты; это ровно наш кейс:
  правило уже даёт направление, а «качество» надо откалибровать.
* **Triple-barrier**: наши TP1/TP2/TP3 + SL + время — уже triple-barrier по
  духу. Значит, лейблы для обучения можно генерить из собственных исходов
  (уже есть в `v3_outcomes`!), и это **самый честный** способ получить
  обучающую выборку без внешних «сценарных» данных.

## 4. Целевая архитектура «отбора» (согласованная, без противоречий)

Ключевой принцип: **ничего не заменяем, а расслаиваем**. «Отбор монет» — это
не один скор, а **четыре отдельных контура**, каждый из которых можно
включать/выключать конфигом и валидировать независимо:

```
[1] UNIVERSE  (фильтры-воронки, БЕЗ скоринга)
    turnover ≥ 20M | спред ≤ 0.35% | OI > 0 | листинг ≥ N дней |
    не synthetic/halting | depth ≥ 250k$    (подключить мёртвые пороги из конфига)

[2] RANK      (кросс-секционный относительный скор — новый)
    RS-моментум (1h/4h/24h/7d vs BTC и vs медиана вселенной, z-score),
    RVOL (объём последнего окна / собственное среднее),
    OI-Δ24h, funding-нейтральность, позиция в 24h-диапазоне,
    волатильность-нормированный ход, возраст листинга (метка, не штраф по факту),
    ликвидность глубины (лучше, чем turnover), спред-качество.
    → TOP-K по rank (K = SCAN_TOP × diversity-множитель)

[3] DIVERSE  (новая корзина)
    иерархическая кластеризация кандидатов по корреляции 30d-доходностей
    (или intraday), max = MAX_CORRELATED_POSITIONS на кластер,
    порог = BTC_CORRELATION_PENALTY_THRESHOLD (0.75);
    кластеры: BTC-beta, ETH-beta, L1, memes, DeFi, perp-«шум» —
    без хардкода секторов, только по корреляционной матрице.

[4] QUALITY  (существующий движок + расширения)
    score_signal (ортогонализованный) → детерминированный гейт →
    калиброванная уверенность (опционально) → публикация.
```

### 4.1 Конкретные изменения в данных (реальные, публичные)

### 4.2 Новые признаки (формулы — стартовые, калибруются)

**RANK-блок (кросс-секционный, вычисляется один раз на скан, не на монету):**
```
rs24  = z( pct24h(coin) − pct24h(BTC) , по всем кандидатам )
rs7d  = z( pct7d(coin) − pct7d(BTC) )
rvol  = vol(15m/pоследN) / mean50(vol(15m))         # нормализация по монете
dpos  = (close − low24h) / (high24h − low24h)        # 0..1 в диапазоне
oiΔ   = oi_now / oi_24h_ago − 1
fund  = clamp(|funding| / 0.001, 0, 1)               # 0 = нейтрально
heat_rank = 0.30*rs24 + 0.20*rs7d + 0.20*rvol + 0.10*oiΔ + 0.10*(1−fund) + 0.10*depth_grade
```
Важно: **rank используется только для очерёдности Stage-2**, направление
(signal direction) остаётся за движком — никакого конфликта с гейтом.

**TimeframeView-расширения (всё уже в `compute_all`):**
```
di_bull = plus_di − minus_di
ema_stack = sign(ema9>ema20) + sign(ema20>ema50) + sign(ema50>ema200)   # −3..+3
bb_pctb, mfi_14, wpr_14, roc_20, macd_cross, stoch_cross, obv_trend, cvd_trend
rv20, atr_pctl (уже есть), vwap24_dist_pct (новый rolling VWAP 24ч)
```

**Dеrivatивы-матрица (новый `PositioningScore` 0–100):**
```
if OI_Δ>0 and price_Δ>0:   позиционирование = «здоровый лонг-билд» (50→70, если funding нейтр.)
if OI_Δ>0 and price_Δ<0 and funding>0: «перегрев лонгов, риск каскада» (→25)
if OI_Δ>0 and price_Δ<0 and funding<0: «шорт-билд, потенциал squeeze» (→70)
if OI_Δ<0 and price_Δ<0:              «капитуляция лонгов — осторожный LONG-признак» (→60)
if OI_Δ<0 and price_Δ>0:              «short-squeeze — осторожный избыточный импульс» (→45)
+ штрафы: ликвидации > X$ за 5 мин (ускорение), L/S < 0.35 или > 0.65, |funding| > порога
```

**Volume profile:**
```
poc, vah, val (70% value area) за 24ч (и за 7д для макро-уровней);
вход «в value area у POC» — нейтрально; «у VAH/у VAL с объёмом» — сетап;
пробой VAH/пробитие VAL с RVOL>1.5 — подтверждение; «тонкая зона» — маркер
быстрого движения (НЕ уровень для входа против).
```

### 4.3 Ортогонализация скоринга

Предлагаю **группировку факторов по смыслу**, чтобы не было дублирования и
чтобы каждая группа была проверяема по исходом отдельно:

| Группа | Факторы | Вес (старт) |
|---|---|---|
| Тренд/структура | ADX+DI-сила, EMA-stack, BOS/CHoCH (исправленный), swing-структура | 25 |
| Моментум/энтропия | RSI-позиция, MACD-hist+кросс, Stoch-кросс, ROC-20, W%R | 15 |
| Объём/флоу | vol_z, RVOL, OBV-тренд, MFI, BB %B, реальная CVD-дельта | 20 |
| Деривативы | PositioningScore (OI×funding×цена), L/S, ликвидации | 15 |
| Волатильность/режим | ATR-pctl, squeeze, regime-флаг, HMM-расхождение | 10 |
| Ликвидность/исполнение | depth-grade, microprice/spread, slippage-прокси | 7 |
| Контекст рынка | BTC/ETH, dominance, глобальная фаза | 8 |

Веса — **не хардкод**: калибруются offline (Optuna → walk-forward с
purge/embargo); в проде остаются из конфига (см. §6.4). Это решает «противоречие
самому себе» из §2.2 без изменения идеологии: скор остаётся интерпретируемой
суммой факторов с `ScoreBreakdown`.

### 4.4 Ответ на «может, индикаторы какие-то?»

Классика, которую **стоит** добавить (все — детерминированные, без будущего):
* **RVOL** (relative volume) — главный «heat»-детектор, которого нет;
* **DI-направленность + EMA-stack** — "тренд-качество" вместо «ADX>22»;
* **MFI** (money flow index) — объёмный RSI, хорошо работает на альтах;
* **BB %B + squeeze дивергенция** — уже посчитаны, экспонировать;
* **Stochastic/MACD-кроссы с фильтром по направлению старшего ТФ** — как
  подтверждение, а не самостоятельный вход;
* **Volume Profile POC/VAH/VAL** и **реальная дельта (CVD из tape)** — как
  описано выше;
* **Funding/OI-матрица** — вместо «funding одиннадцатый признак».
Индикаторы, которые **не добавляем**: «магические» комбинации типа
«RSI 30 + MACD cross + stoch 20» без валидации, Эллиотт-волны как сигнал
(у нас они есть как контекст — оставляем контекстом), «гарантированные»
энтрис-модели из проприетарных скриптов.

## 6. Ключевые решения, которые надо принять явно

### 6.1 Почему мы НЕ «просто добавляем индикаторы» в первую очередь

Потому что в текущем скоринге 30+ признаков уже посчитаны, но `TimeframeView`
пропускает 18 из них, а скоринг использует 12. Сначала **экспонировать и
использовать** существующий информационный запас, потом добавлять новые
данные. Это дешевле и не создаёт «слона из мухи» (риск: если сразу включить
50 индикаторов, мы получим переобучение и невозможность интерпретации).

### 6.2 Purge/embargo — почему это критично (и для чего именно)

Важная точность: текущая `walk_forward` **не обучает параметры** — она гоняет
один и тот же детерминированный движок на последовательных окнах, поэтому как
«проверка устойчивости правил» она корректна. Purge/embargo становится
обязательным, как только мы начинаем **подгонять что-то по данным**
(веса P2-2, калибровка, ML-модель): тогда у тестовых баров первые 100–200 баров
«опираются» на индикаторный хвост (EMA-200, atr_pctl, zigzag) из тренировочных
данных, а fold-окна у нас идут встык. Правило:
```
test_start ≥ train_end + embargo_bars
embargo_bars ≈ max(индикаторный warm-up) ≈ 200 баров entry-TF (≈50ч на 15м)
```
Это стандарт для продвинутых (PyBroker, FreqAI-экосистема, López de Prado).

### 6.3 Как честно валидировать orderflow/деривативы (без фиктивных данных)

А) **Live-валидация**: WS-признаки пишутся в `features` (они уже туда идут),
исходы в `v3_outcomes`; калибровка по фактору по мере накопления. Это путь для
всех микроструктурных улучшений.
Б) **Backtest-режим «derivatives-aware»**: подтягивать **исторический funding**
(публичный `/v5/market/funding/history`, Bybit v5 — подтверждено) и **OI из
live-накопления** (если бот работал: у нас `_oi_history` уже пишется; можно
научить `history()` отдавать его за период). По публичному API **исторического
OI у Bybit нет** (`/v5/market/open-interest` — только текущий) — поэтому в
бэктесте OI-матрица будет помечаться «н/д», а не подставляться. Это
согласуется с политикой «без синтетики».
В) Для orderflow: исторических принтов по публичному API нет (15м глубина
`recent-trade` и тапей в WS живьём). Значит, **бэктест не может проверить
микроструктуру** — фиксируем это в документации и в метриках
(«microstructure covered: live-only»), иначе parity-обещание станет ложью.

### 6.4 Калибровка весов — процедура, а не «магия чисел»

1. Собираем признаки всех когда-либо опубликованных сигналов (уже в SQLite).
2. Для каждого бакета (или с fit-моделью) считаем P(win), среднее R, CI.
3. Если модель (например, logistic на 8 факторах) даёт **на purge/embargo
   CF-разбиениях** стабильный IC (information coefficient) > порога — тогда
   можно уточнять веса; иначе веса остаются 50/50-консервативными.
4. Публикуем в отчёте: «факторы: тренд — 0.03 R/бакет, объём — 0.07, OI — −0.02»
   — прозрачно и проверяемо.
5. **Никаких** «подкрутил — стало лучше на том же срезе»: каждый твик проходит
   walk-forward (P2-1).

### 6.5 Противоречия, о которых надо сказать прямо

* **Инвариант №3** («AI не меняет direction/levels/score») конфликтует с
  желанием «ML-фильтра качества». Разрешение: ML-модуль в v3 **по умолчанию
  OFF**, живёт в отдельном `v3/ml/`, и если включается — он меняет **только**
  отображаемую «калиброванную уверенность» и **не** трогает гейт; либо явно
  пересматриваем инвариант (требует валидации ML-1 и отдельного решения).
* **Парадокс «лучших возможностей»**: качественный скоринг + «просто показать
  топ-20» = одна коррелированная корзина. Поэтому diversity — обязательная
  часть P0/P2-3, иначе P1-3 (деривативы) будет уводить в одну тему (например,
  всё в memes при отрицательном funding).
* **«Heat сканера» vs «сигнал движка»**: rank задаёт *очерёдность*, сигнал
  задаёт *направление*. Смешение этих двух ролей — главная причина «отбора
  плохих монет», и оно уже есть (heat 45% = 24h %).
* **Честность про производные**: CoinGlass heatmap — модельные оценки; долю
  реальных ликвидаций от WS можно использовать как **проверку** heatmap-зон
  (validate), но не наоборот.
* **Backtest без деривативов**: пока бэктест не видит funding/OI/стакан, любые
  улучшения этих блоков «недоказуемы» в бэктесте — честно маркируем
  (см. 6.3) и не выдаём parity-обещание шире, чем оно есть.

## 7. Что НЕ делать (анти-рекомендации)

1. **Не заменять детерминированный гейт на ML-предсказание** без пересмотра
   инвариантов и walk-forward валидации (ML-1 + пересмотр инварианта №3).
2. **Не добавлять синтетические/демо-данные** ни в бэктест, ни в live — даже
   «чтобы показать красиво» (нарушает политику платформы и тесты
   `test_realdata.py`).
3. **Не вводить TA-Lib/новые тяжёлые зависимости** ради индикаторов, которые
   мы уже считаем в numpy (лучше — своя чистая реализация + тесты на свойства).
4. **Не включать CoinGlass/Coinalyze как обязательный провайдер** —
   только опциональный контекст с пометкой «модельные оценки» и обязательной
   вспомогательной ролью. Нет ключей → нет данных → ничего не ломается.
5. **Не делать «соцсети → сигнал»**: новости/сентимент остаются контекстом
   (сейчас так и есть); соцсигнал не верифицируем и легко «закармливается».
6. **Не оптимизировать пороги на полной выборке** (overfit). Только
   walk-forward + purge/embargo + bootstrap CI.
7. **Не упрощать риск-движок под «более качественный отбор»**: правило «плечо
   из волатильности, $риск из депозита» — правильное; калибровка качества
   может лишь **уменьшать** размер (risk_pct × k, k≤1), не увеличивать.
8. **Не добавлять «режим монеты прошёл +20% → top»** — это уже есть в heat и
   это главный источник «покупаем вершину». Вместо этого — RS **относительно
   BTC** и позиция в диапазоне.
9. **Не менять названия существующих полей без миграции**: `taker_buy_sell_ratio`
   на самом деле account ratio — исправить название честно (`account_long_ratio`),
   но с сохранением обратной совместимости API (поле остаётся, добавляется
   правильное).
10. **Не строить «L2-карту стен» из снапшотов REST 1 раз в 60с** — это уже
    выборка, а не поток; нужны дельты WS. Иначе получим «карту прошлого».

## 8. Метрики успеха (что считаем «лучше»)

| Метрика | Как мерить | Цель |
|---|---|---|
| Winrate по бакетам score | калибровка по `v3_outcomes` | монотонность: score↑ → winrate↑ |
| Calibration error | |E[P(win)] − фактический winrate| | < 5 п.п. |
| Информация по факторам | IC каждого фактора с исходом | выделить 2–3 реально работающих |
| Значимость walk-forward | доля folds с expectancy>0; CI | > 60% folds, нижняя граница PF>1.0 |
| Chase-коэффициент | доля топ-сетапов с входом в верхней 25% 24h-диапазона | снизить (меньше «покупаем верх») |
| Диверсификация | ср. max-корреляция выбранной корзины | < 0.75 (порог из конфига) |
| Дрейф качества | CUSUM на скользящем winrate | сигнал деградации → отчёт |
| Sets/scan (частота, не качество) | как сейчас | не ухудшать резко (контроль) |

## 10. Вывод

Раунд 5 уже закрыл самые рискованные для качества ошибки времени входа:
закрытые свечи, честный RVOL, подтверждение давления и исключение exhausted
движений; плюс daemon теперь действительно ищет по всей вселенной.
Следующие вещи дадут прирост качества при контролируемом риске:

1. **P1 — реальная микроструктура** поверх WS-инфраструктуры: настоящий CVD,
   дельты, крупные принты, microprice, book slope и поглощение. Это то, что
   отличит «ранний свечной сканер» от полноценного order-flow анализа.
2. **P1 — volume profile**: POC/VAH/VAL из реальных 1m/5m свечей для entry и
   TP, но только с отдельным backtest, потому что уровни меняют механику входа.
3. **P2 — замкнуть контур качества**: калибровка score→исход, purge/embargo,
   bootstrap CI, Monte Carlo и статистический тест «правило против случайных
   входов». Только после этого — опциональный ML-мета-слой (OFF по умолчанию).

Нельзя объявлять эти следующие этапы готовыми без исторической проверки:
деривативный OI/funding и live-only order flow пока не покрыты полноценным
историческим бэктестом.

Всё это спроектировано так, чтобы **не конфликтовать** с текущими инвариантами:
детерминированный гейт остаётся главным, AI-слой — только объяснения,
данные — только реальные, бэктест — без look-ahead, а новые пороги — всегда
после walk-forward валидации.
