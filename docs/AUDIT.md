# Аудит проекта (до модернизации)

Дата: 2026-08-31. Репозиторий: `artyr180598-gif/hype-martingale-bot` (ветка `arena/01a0589d-hype-martingale-bot`).

## Что уже есть (сохраняем)

* **v3-движок** (`v3/engine.py`) — детерминированный `LONG / SHORT / NO_TRADE`-гейт,
  общий код для live и backtest (backtest/live parity). Хорошая идея — сохраняем.
* **Data kernel** (`src/data/`) — Bybit / Binance / MEXC с фейловером, публичные
  данные без ключей, демо-рынок, нормализация/дедупликация свечей,
  `EnrichedSource` (CoinGecko, Fear&Greed, новости). Сохраняем.
* **Аналитика** (`v3/analysis/*`) — multi-timeframe, regime, derivatives, orderflow,
  scoring с факторным разбором, levels, risk. Сохраняем (дорабатываем).
* **Backtest / walk-forward / calibration** (`v3/backtest.py`, `v3/walkforward.py`,
  `v3/calibrate.py`) — fees/slippage/funding, без look-ahead (вход на открытии
  следующего бара). Сохраняем.
* **Lifecycle + SQLite** (`v3/store.py`) — cooldown, активные сигналы, исходы
  TP1/TP2/TP3/SL. Сохраняем.
* **AI-слой** (`v3/ai.py`) — rule-based по умолчанию + опциональный OpenAI;
  не может менять direction/levels/score. Сохраняем.
* **Observability + API** (`v3/observability.py`, `v3/api.py`). Сохраняем (расширяем).

## Раунд 7 (2026-09-02): проверка на РЕАЛЬНЫХ данных биржи

До этого раунда всё, что утверждалось о поведении бота «вживую», было проверено
только синтетикой: юнит-тесты и бэктест вызывают `evaluate_bundle()` напрямую и
**не проходят** участок `analyze()`, который работает с сетью и свежестью данных.
Прямого выхода в интернет из sandbox нет (TLS EOF ко всем биржам), поэтому
реальные данные сняты через веб-прокси с публичного REST OKX v5
(`BTC-USDT-SWAP`, 2026-09-02 ~11:52 UTC) и сохранены дословно в
`v3/tests/fixtures/okx_btcusdt_swap_capture.json` (5 таймфреймов × 60 свечей,
тикер, ставка финансирования, открытый интерес, стакан 12 уровней).

Инструмент: `v3/replay.py` — прогон снапшота через живой путь
(`SnapshotSource → FuturesDataService → FuturesSignalEngine.analyze →
render_signal + assess_confidence + evaluate_alert`), без сети и без синтетики.
Часы фиксируются на моменте съёма. Команды: `python -m v3 replay <файл>`
(`--walk N --step M`, `--mode pro`, `--json`), `python -m v3 record BTCUSDT`.

### Найдено и исправлено: P0 — движок почти всегда считал данные устаревшими

* **Симптом (замер на реальных свечах).** В любую минуту часа какой-нибудь
  таймфрейм попадал в `degraded` как `stale klines (…)`, отсюда `stale=True`,
  `no_trade_reasons = ["stale kline data"]` и `NO_TRADE`. Замер по одному часу
  реальных данных: 0–1 мин → `stale klines (4h)`, 2–3 мин → `(5m)`,
  10–20 мин → `(15m)`, 30–45 мин → `(1h)`. То есть входа не было практически
  никогда, а авто-сигналы (`ALERT_REQUIRE_FRESH=true`) блокировались всегда.
* **Причина.** Проверка сравнивала **время открытия** последней закрытой свечи
  с `tf + MAX_DATA_AGE_SECONDS` (`MAX_DATA_AGE_SECONDS=120`). Закрытая часовая
  свеча по построению имеет «возраст от открытия» от 60 до 120 минут, поэтому
  правило срабатывало в 58 из 60 минут каждого часа; для 15m — в 13 из 15.
* **Почему не ловилось тестами.** `evaluate_bundle()` (live-паритет и бэктест)
  эту проверку не содержит, а сетевые прогоны в sandbox недоступны.
* **Исправление (`v3/engine.py`).** Сервис данных отдаёт только закрытые свечи,
  поэтому свежие данные = «последняя закрытая свеча закрылась не раньше одного
  таймфрейма назад»: `now - (last_open + tf) <= tf + MAX_DATA_AGE_SECONDS`.
  Правило не зависит от эпохи биржи (первая версия фикса через `now // tf_ms`
  ломалась на суточных свечах OKX — сутки там начинаются в 00:00 UTC+8).
  Возраст данных в fallback тоже считается от **закрытия** свечи.
* **Проверка после фикса.** Тем же замером: 0/1/2/3/10/20/30/45/58 минут —
  `stale klines` нет ни на одном таймфрейме, `stale=False`. Проверка не
  выключена: на искусственно «отстающем» графике (сняты 3 последние свечи
  5m/15m/1h) `stale klines` по-прежнему появляется и сигнал гасится.
* **Регрессия.** `v3/tests/test_replay_realdata.py` (12 тестов на реальном
  снапшоте): целостность фикстуры, нормализация символа `BTC-USDT-SWAP →
  BTCUSDT`, прогон движка, отсутствие ложного `stale` в 8 точках часа,
  отстающий график всё ещё виден, возраст данных от закрытия свечи, честное
  «н/д» по неснятым источникам, молчание на слабом сетапе, отсутствие
  look-ahead в проходе по истории.

### Что показал прогон на реальных данных

* BTC-USDT-SWAP, 2026-09-02 11:52 UTC, цена 76607.2, фандинг 0.0001,
  открытый интерес 2 260 869 691 $, спред стакана 0.1 $ (12 уровней).
* Итог движка: `NO_TRADE`, оценка сетапа 36/100 (тир NONE), уверенность бота
  45% — «низкая», полнота данных 90%, риск 4/10, режим рынка UNCERTAIN.
  Разбор уверенности: качество 36.0, данные 90.0, таймфреймы 50.0,
  объём/стакан 55.8, риск 36.0, импульс 52.0 (подогрев 40/100).
* Авто-сигнал: промолчал бы (нет направления, качество 36 < 78, уверенность
  45% < 70%, R:R 0.00 < 1.8, нет стопа и целей) — пороги сработали как задумано.
* Проход по истории (8 точек за 6 часов реальных свечей): качество 36–45,
  уверенность 42–45%, ни одного ложного сигнала — на падающем/боковом BTC бот
  молчит, а не выдумывает вход.
* Честные деградации: `global context unavailable` (CoinGecko в снапшот не
  снимался) — показатель «н/д», а не подмена.

### Честно не проверено

* Реальные источники Bybit/Binance/MEXC в этом раунде не опрашивались

## Раунд 8 (2026-09-02): бэктест на РЕАЛЬНЫХ свечах — бот находит сетапы и проигрывает

Раунд 7 доказал только одну сторону: на реальных данных бот **молчит**
(`NO_TRADE`, 8 точек прохода по истории). Оставался непроверенным главный
вопрос пользователя — **способен ли бот вообще найти сетап на живом рынке** и
чем бы это кончилось. Ответ нужен был не «по юнит-тестам», а на реальных барах.

### Что сделано

* Снята длинная реальная серия: `GET https://www.okx.com/api/v5/market/candles?instId=BTC-USDT-SWAP&bar=15m&limit=300`
  (2026-09-02), 300 свечей 15m, 2026-08-30 09:45 → 2026-09-02 12:30 UTC.
  Сохранена дословно, без правок: `v3/tests/fixtures/okx_btcusdt_15m_300.json`
  (30 403 байта, `kind: okx_candles_v1`, сетка ровно 900 000 мс без пропусков,
  одна недоформированная свеча `confirm="0"`).
* Добавлен офлайн-путь в прод-бэктестер: `v3/replay.py::load_candles_series`
  (отбрасывает недоформированную свечу — иначе это look-ahead) и
  `run_replay_backtest`, который зовёт **тот же** `v3.backtest.run_backtest`,
  что и команда `backtest`: та же комиссия 0.055%, слиппедж 0.02%,
  пессимистичная проверка стопа, частичные выходы, funding-перенос.
* Команда: `python -m v3 replay <серия.json> --backtest [--warmup N] [--json]`.

### Найденное противоречие (виден только на реальных данных)

* В сделках бэктестера полнота данных всегда **ровно 0.30**. Причина — не рынок,
  а конструкция: `v3/engine.py::data_confidence` снимает 0.1 за каждую из трёх
  честных деградаций бандла (`funding/order book/global context unavailable`),
  0.2 за пустой стакан, 0.1 за `btc_trend == "flat"` и 0.1 за `funding_rate is None`.
* Живой гейт публикации (`v3/validator.py`) требует `signal.confidence >=
  CONFIDENCE_MIN = 0.45`, а `v3/backtest.py` кладёт `min_confidence` в
  `BacktestConfig`, но `simulate_trade` эти поля (`min_confidence`, `min_score`)
  **не применяет** — они только сериализуются. То есть бэктест показывает
  сетапы, которые прод-валидатор не опубликовал бы.
* Почему не «починили» молча: при искусственном бандле полнота 0.30 постоянна,
  поэтому применение этого гейта обнулило бы любой бэктест и сделало
  инструмент бесполезным. Вместо этого бэктест **печатает разрыв явно**: сравнивает сетапы
  только по рыночным критериям (качество ≥55, R:R ≥1.8, риск ≤6, целей ≥2 —
  прошли 5 из 5) и отдельно по порогам авто-сигнала (качество ≥78, уверенность
  ≥70%, R:R ≥1.8, риск ≤6 — **0 из 5**), а про полноту данных пишет
  предупреждение. Лучший сетап серии: качество 61, уверенность 57.8%.
* Побочный баг отчёта исправлен: строка сделки печатала `увер. 0.3%`, смешивая
  сводный процент бота (56.5%) с полнотой данных 0..1 (0.30). Теперь обе цифры
  на своих местах (`увер. 56.5% · данные 30%`).

### Проверка

* `v3/tests/test_replay_realdata.py`: 18 тестов (было 12) — целостность серии
  (300 строк, 9 полей, равномерная сетка, одна forming-свеча, непротиворечивый
  OHLC), отбрасывание недоформированной свечи, отказ чужого формата, чтение
  приложенного разбора уверенности, **исполнение бэктестера на реальной серии
  с 5 сетапами**, флаг `--backtest` в CLI.
* `.venv/bin/pytest -q` → **161 passed**; `.venv/bin/ruff check .` → чисто.

### Честно не проверено

* Один символ (BTC) и один интервал (3 дня). Для вывода о «находит монеты ДО
  движения» нужна серия по многим монетам и более длинная история — на 300
  свечах 15m макро-ТФ 4h даёт только 20 баров и бэктестер его отбрасывает
  (движок работал на 15m + 1h; это видно в шапке отчёта).
* Funding, стакан, ликвидации и глобальный контекст в серии отсутствуют,
  поэтому факторы, зависящие от них, в бэктесте не участвовали (в live —
  участвуют). Метрики описывают «чистую» механику входа, а не полный прод-путь.
* Результаты на прошлых данных не гарантируют будущих.
